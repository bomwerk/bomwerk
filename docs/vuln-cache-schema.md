# Vulnerability cache schema

This documents `src/vuln/cache.cpp`'s SQLite file (default
`$XDG_CACHE_HOME/bomwerk/vuln_cache.sqlite3`, fallback `~/.cache/bomwerk/`): every table it
holds, what each column means, and the schema-version history, so the cache can be read and
reasoned about with a plain `sqlite3` shell, without opening a line of C++. It is generated by
hand alongside `src/vuln/cache.cpp`'s `kSchemaV1Sql`/`kSchemaV2Sql`, and
`tests/unit/test_vuln_cache.cpp` asserts the live table/index list against the list documented
here (`expected_schema_object_names`), so this file drifting from the code fails a test rather
than silently going stale.

## Inspecting your cache

```bash
sqlite3 ~/.cache/bomwerk/vuln_cache.sqlite3 "PRAGMA user_version;"
sqlite3 ~/.cache/bomwerk/vuln_cache.sqlite3 ".tables"
sqlite3 ~/.cache/bomwerk/vuln_cache.sqlite3 "SELECT feed_name, datetime(fetched_at, 'unixepoch'), version_label, record_count FROM feed_state;"
sqlite3 ~/.cache/bomwerk/vuln_cache.sqlite3 "SELECT COUNT(*) FROM vuln_cache;"
```

## Schema-version history

`PRAGMA user_version` is the number to check first: it names which of the tables below a given
cache file actually has on disk.

| Version | What changed |
| --- | --- |
| 1 | `vuln_cache`: the OSV/NVD per-key response cache. |
| 2 | Adds `feed_state` and `osv_advisory_snapshot`. Strictly additive: every v2 statement is `CREATE ... IF NOT EXISTS`, and no v1 table or row is touched. `VulnCache::open()` migrates an existing v1 file to v2 in place, inside one transaction, so a step failing partway leaves the file exactly as it was. A file stamped with a version newer than the running binary understands is refused outright, unchanged from v1's behavior. |

## `vuln_cache` (v1)

The per-key OSV/NVD response cache. One row per query key; `payload` is the upstream response
object stored verbatim (as canonical, sorted-key JSON), so any field not yet extracted into a
typed column stays recoverable later without a re-fetch.

```sql
CREATE TABLE IF NOT EXISTS vuln_cache(
  purl       TEXT PRIMARY KEY,
  fetched_at INTEGER NOT NULL,
  payload    TEXT NOT NULL);
```

| Column | Type | Meaning |
| --- | --- | --- |
| `purl` | TEXT | The query key. Despite the name, this is a **namespaced key**, not always a bare purl: OSV detection entries use the query purl as-is; a full-advisory hydration entry appends a `0x1F` (unit separator) byte + `"full"`; an NVD CPE-match entry appends `0x1F` + `"nvd"`; a per-CVE NVD enrichment entry appends `0x1F` + `"nvdcve"`. `0x1F` never appears in a real purl or CPE string, so no namespace can collide with another. |
| `fetched_at` | INTEGER | Unix epoch seconds (UTC) when this entry was fetched. Compared against a caller-supplied freshness horizon (24 h by default) to decide whether to re-fetch; an entry past the horizon is still used, with a warning, under `--offline`. |
| `payload` | TEXT | The upstream JSON response, verbatim, as canonical (sorted-key) `nlohmann::json::dump()`. |

Expected size: scan-dependent, one row per queried purl/CPE/CVE. A few hundred to a few thousand
rows for a typical repository.

## `feed_state` (v2)

One row per **bulk feed**, not per purl: the idempotency ledger a bulk-feed consumer reads and
writes through `VulnCache::lookup_feed_state`/`store_feed_state`, to decide whether its next
refresh needs to transfer anything at all. Nothing in this repository populates it yet; it is
here so that consumer, wherever it lives, shares one cache file and one migration path with the
per-purl cache above instead of inventing its own.

```sql
CREATE TABLE IF NOT EXISTS feed_state(
  feed_name      TEXT PRIMARY KEY,
  fetched_at     INTEGER NOT NULL,
  changed_at     INTEGER NOT NULL,
  etag           TEXT NOT NULL DEFAULT '',
  last_modified  TEXT NOT NULL DEFAULT '',
  content_digest TEXT NOT NULL DEFAULT '',
  record_count   INTEGER NOT NULL DEFAULT 0,
  version_label  TEXT NOT NULL DEFAULT '') WITHOUT ROWID;
```

| Column | Type | Meaning |
| --- | --- | --- |
| `feed_name` | TEXT | Stable identifier, owned by whichever component refreshes that feed. A compatibility surface: never renamed without a migration step, since it is a key in a user's on-disk file. |
| `fetched_at` | INTEGER | Unix epoch seconds (UTC) this feed was last **asked about**, whether or not anything changed. Compared against a caller-supplied freshness horizon to decide whether a refresh call issues a request at all. |
| `changed_at` | INTEGER | Unix epoch seconds (UTC) this feed's content last actually **moved** (a `200` with new bytes, not a `304` or a digest match). What an auditor asking "how old is your exploited-vulnerability data?" wants, distinct from `fetched_at`. |
| `etag` | TEXT | The `ETag` response header from the last successful fetch, sent back as `If-None-Match` on the next refresh. Empty when the server never sent one. |
| `last_modified` | TEXT | The `Last-Modified` response header, sent back as `If-Modified-Since`. Empty when never sent. A feed that serves this and honors it (verified: a conditional GET with a matching value returns `304`). |
| `content_digest` | TEXT | A 64-bit FNV-1a digest of the last successfully fetched body, as lowercase hex. The idempotency fallback for a feed serving neither validator above: a change detector, not a security control (authenticity is TLS's and the endpoint allowlist's job). |
| `record_count` | INTEGER | Rows currently held for this feed, as counted after the last successful load. |
| `version_label` | TEXT | A human-meaningful version string for this feed's last successful load: a feed's own catalogue version when it publishes one, or (when it does not) the same digest as `content_digest`. |

Expected size: one row per bulk feed the running build refreshes.

## `osv_advisory_snapshot` (v2)

What OSV said about each purl's advisory set as of the last refresh: the memory a delta diff
compares against. Deliberately redundant with `vuln_cache`'s stored payloads (which remain the
verbatim source of truth): if this table were ever wrong, it is disposable and rebuildable by
re-parsing the cached payloads.

```sql
CREATE TABLE IF NOT EXISTS osv_advisory_snapshot(
  purl          TEXT NOT NULL,
  advisory_id   TEXT NOT NULL,
  modified      TEXT NOT NULL,
  first_seen_at INTEGER NOT NULL,
  last_seen_at  INTEGER NOT NULL,
  PRIMARY KEY(purl, advisory_id)) WITHOUT ROWID;
```

| Column | Type | Meaning |
| --- | --- | --- |
| `purl` | TEXT | The component purl this advisory was seen against. |
| `advisory_id` | TEXT | One advisory id (`CVE-…`/`GHSA-…`/`OSV-…`) OSV's querybatch reported for `purl`. |
| `modified` | TEXT | OSV's own `modified` timestamp for this advisory, stored **verbatim** and compared for **equality only**, never parsed as a date. OSV documents it as RFC3339, but a feed is untrusted input, and equality is all the delta needs. |
| `first_seen_at` | INTEGER | Unix epoch seconds (UTC) this `(purl, advisory_id)` pair was first observed. Preserved across updates that change `modified`, so a consumer that classifies an advisory as new versus already-seen can rely on it surviving a refresh that only confirms the advisory still applies. |
| `last_seen_at` | INTEGER | Unix epoch seconds (UTC) of the most recent refresh that still reported this pair. |

Expected size: scan-dependent, roughly one row per vulnerable purl times its advisory count.
