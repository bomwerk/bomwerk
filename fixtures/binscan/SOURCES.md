# fixtures/binscan: where the binaries come from

The ELF images and `ar` archives this case needs are **generated by
`scripts/run_binscan_case.py` into the temporary copy**, not committed here.
Three reasons, in order of how much they matter:

1. **CI runs macOS as well as Linux.** A binary produced by the host toolchain
   would be Mach-O there and ELF here, so a committed "real" artifact would
   either be a Linux binary the macOS job cannot meaningfully exercise, or two
   artifacts asserting two different things. Generated bytes are identical on
   both runners, so the case asserts one answer everywhere.
2. **A committed binary cannot be reviewed.** This is a security tool; an
   opaque blob in the fixture set is exactly the thing a reader has to take on
   faith. The generator is ~100 lines of readable Python stating precisely
   which `DT_NEEDED` entries, sonames, symbols and archive members each
   artifact carries, and a reviewer can check the assertion against it.
3. **The interesting artifacts are not ones a compiler emits anyway.** The
   statically linked output is the case the diagnostics design exists for, and
   pinning it means controlling the file rather than hoping the local toolchain
   links one that way.

The same reasoning drives the unit tests, which build every image through
`tests/support/elf_builder.hpp` and `tests/support/archive_builder.hpp`.

`trace.jsonl` carries `@FIXTURE_ROOT@` placeholders because a real trace
records ABSOLUTE paths, which cannot be committed to a repository that gets
checked out somewhere different every time. The harness substitutes the
temporary copy's own path, exactly as fixtures/trim/trace.jsonl is
treated.
